## 1. 프로젝트 개요

- **목표**
  - xv6 커널에 fault injection 및 CoW fork 관련 시나리오(refcount race 등)를 구현·검증한다.
  - Go 기반 Bubble Tea CLI를 통해 QEMU 실행과 테스트 결과(성공/실패/panic)를 실시간으로 확인한다.
  - 커널 개발의 테스트·디버깅 과정을 효율화한다.
- **배경**: 커널 단위 테스트를 수동으로 QEMU 콘솔에서 확인하는 방식은 반복 실행/디버깅 비용이 큼.
  따라서 테스트 실행과 결과 확인을 자동화하는 CLI 도구를 제공한다.
  CLI가 QEMU 프로세스를 래핑해 로그를 구조화하여 보여주면 커널 개발 피드백 루프가 빨라진다.
- **범위(In-scope)**
  - xv6 커널: fault injection 테스트 케이스, CoW fork 관련 race 시나리오
  - CLI: QEMU 실행/타임아웃 처리, 실패 로그 파싱 및 TUI 표시
  - 문서: 라이선스 스캔, 기여 가이드, 최종 보고서
- **범위 외(Out-of-scope, 필요 시 조정)**
  - xv6 외 다른 커널/OS 지원
  - CLI의 원격/분산 실행 (단일 로컬 QEMU 인스턴스 기준)

> ⚠️ 위 목표/범위는 가정입니다. 실제 프로젝트 요구사항과 다르면 리뷰 코멘트로 수정 요청 부탁드립니다.

## 2. 프로젝트 구조

```
.
├── kernel/          # xv6 fork + 결함 시나리오 + 스케줄링 교란 훅(scheduler perturbation hook) (김수아)
├── cli/             # Go CLI + Bubble Tea + 로그 파싱/리포트 생성기 (최우주)
├── docs/            # 개발계획서, 진행보고서, 라이선스 점검 기록 (정수민)
├── .github/         # 이슈/PR 템플릿, CI 워크플로우
├── README.md        # 프로젝트 소개 및 실행 방법
├── CONTRIBUTING.md  # 기여 가이드 (커밋/브랜치 규칙)
└── LICENSE          # 프로젝트 라이선스
```

- `kernel/`은 fault injection 코드와 스케줄링 교란 훅(scheduler perturbation hook)을 포함 (단순 시나리오 추가를 넘어, 실행 타이밍 자체를 조작하는 훅이 있다는 점이 핵심)
- `cli/`는 실행(runner) + 파싱(parser) + 리포트 생성까지 담당 (TUI 표시는 그중 일부)
- `docs/`는 계획서 외에 진행보고서·라이선스 점검 기록을 지속적으로 축적
- `.github/` CI 워크플로우는 **[TBD — 최우주 확인 필요]** build / test / lint / license check 중 무엇을 돌릴지 확정 필요 (우선 build+test부터 시작해 점진적으로 확장 예정)

## 3. 시스템 아키텍처 / 데이터 흐름

```
┌─────────────┐      ┌────────┐      ┌────────────┐
│   cli/      │ ──▶  │  QEMU  │ ──▶  │  xv6 kernel │
│ (runner)    │      │        │      │ (fault      │
└─────────────┘      └────────┘      │  injection) │
      ▲                                └─────┬──────┘
      │                                      │ stdout (structured log)
      │                                      ▼
┌─────────────┐      ┌────────────┐    ┌────────────┐
│ report 생성  │ ◀──  │ bubbletea  │ ◀──│ log parser │
│ (docs 연동)  │      │    UI      │    │ (cli/)     │
└─────────────┘      └────────────┘    └────────────┘
```

- **역할 분리**: `kernel/`은 사람이 읽기 위한 로그가 아니라 **구조화된(structured) 로그**를 stdout으로 출력하는 것이 목표
- `cli/`는 이를 받아 (1) 파싱 → (2) TUI 렌더링 → (3) 필요 시 리포트 파일 생성 순으로 처리
- 리포트 형식: **[TBD — 최우주 확인 필요]** Markdown / JSON / HTML 중 확정 필요 (문서 연동을 고려하면 Markdown이 유력 후보)

## 7. 구현 상세 / 인터페이스 정의

> ⚠️ 아래 굵게 표시된 정의(fault injection 종류, CoW race 종류, 타임아웃 값)는 실제 구현 담당자(김수아·최우주)가 확정해야 하는 부분입니다. 현재는 계획서 논의를 위한 자리표시(placeholder)입니다.

### 7.1 Fault Injection 정의
- Fault injection은 커널 내부에 refcount corruption, allocation 실패 등을 **인위적으로 발생시켜** 오류 처리 경로를 검증하는 테스트 기능
- **[TBD — 김수아 확인 필요]** 실제로 다룰 fault 종류 (예: page fault 유도 / malloc 실패 시뮬레이션 / refcount 강제 조작 / panic 유도 중 어떤 것을 1~3주차에서 구현할지)

### 7.2 CoW Fork Race 시나리오
- Copy-on-Write fork 과정에서 발생 가능한 race condition을 검증
- **[TBD — 김수아 확인 필요]** 아래 중 어떤 race를 우선 구현할지 확정
  - refcount race (동시 fork 시 페이지 참조 카운트 불일치)
  - concurrent fork (동시에 여러 fork 호출 시 페이지 공유 충돌)
  - concurrent exit (fork 중 부모/자식 프로세스 종료 타이밍)
  - page free timing (참조 카운트가 0이 되기 전/후 시점의 free 처리)

### 7.3 로그 포맷 (커널 → CLI, structured text log)
- 로그 라인 포맷(예시): `[LEVEL] test=<name> result=<pass|fail|panic|timeout> detail=<msg>`
- 실제 로그 예시:
  ```
  [PASS] test=cow
  [FAIL] test=refcount detail=expected 1 got 2
  [PANIC] test=refcount detail=page refcount mismatch
  [TIMEOUT] test=concurrent_fork detail=no response in 10s
  ```
- CLI 파서는 이 포맷을 기준으로 TUI에 pass(녹색)/fail(노랑)/panic(빨강)/timeout(회색) 상태를 색상별로 표시
- 포맷 변경 시 반드시 PR에 `#interface-change` 명시

### 7.4 타임아웃 정책
- **[TBD — 최우주 확인 필요]** 기준값 예시: 10초 이상 응답(로그 출력) 없으면 timeout으로 간주 (예시값이며 실측 후 조정 가능), QEMU 프로세스 SIGKILL로 강제 종료 후 `[TIMEOUT]` 상태로 기록
- 무한루프 vs 단순 지연을 구분할지 여부도 2주차(로그 포맷 확정 목표) 논의에서 확정 필요

### 7.5 테스트 성공/실패 기준
- 모든 테스트는 아래 4가지 상태 중 하나로 귀결되며, 통합 테스트는 이 4개 상태 전부를 확인하는 것을 목표로 한다.

| 상태 | 의미 |
|---|---|
| PASS | 시나리오가 기대대로 정상 처리됨 |
| FAIL | 결과 값이 기대와 다름 (커널이 죽지는 않음) |
| PANIC | 커널이 panic으로 중단됨 |
| TIMEOUT | 정해진 시간 내 결과가 나오지 않음 (무한루프/데드락 의심) |

### 7.6 Bubble Tea 선택 이유
- 터미널 환경에서 QEMU stdout 스트림을 실시간으로 읽어 테스트 실행 상태와 결과를 화면에 갱신·표시하기 위해 Bubble Tea(Go TUI 프레임워크)를 사용한다.

### 8.1 신규 의존성 도입 전 사전 확인 (1단계)

- 새로운 Go 패키지를 `go.mod`에 추가하기 **전에**, pkg.go.dev 또는 해당 패키지 저장소의
  LICENSE 파일에서 라이선스를 먼저 확인한다.
- GPL/AGPL 계열로 확인되면 도입하지 않고 대체 라이브러리를 검토하며, 정수민에게 공유한다.
- 확인이 끝난 패키지만 `go.mod`에 추가하고, 이후 PR 단계에서 `go-licenses check`(2단계)가
  최종 검증한다.

### 8.2 PR 시 자동 검증 (2단계)
- CLI(Go) 의존성은 `go-licenses`로 검사한다. 신규 Go 패키지 추가 시:
  ```bash
  cd cli
  go install github.com/google/go-licenses@latest
  go-licenses check ./... 2>&1 | tee ../docs/license-check-$(date +%Y%m%d).log
  ```
- GPL/AGPL 계열 발견 시 정수민에게 즉시 공유 → 대체 라이브러리 검토
- 커널(C) 코드에 외부 코드를 가져올 때는 `go-licenses`가 적용되지 않으므로, 해당 프로젝트의 LICENSE/SPDX 정보를 직접 확인한다 (GPL/AGPL 계열이면 정수민에게 즉시 공유 → 대체 코드 검토)
