# RaceGrader 중간보고서

## 1. 프로젝트 개요
- **프로젝트명**: RaceGrader — xv6 커널 대상 CLI 기반 동시성 결함(concurrency fault) 탐지 자동 채점기
- **목적**: 커널 단위 테스트를 수동으로 QEMU 콘솔에서 확인하는 방식은 반복 실행·디버깅 비용이 크다. RaceGrader는 스케줄링 타이밍을 매번 다르게 흔들며 반복 실행해, 겉보기엔 통과했지만 실제로는 락 누락·race condition이 있는 코드를 찾아낸다. CLI가 QEMU 실행과 결과 파싱을 자동화해 커널 개발의 테스트·디버깅 피드백 루프를 단축하는 것을 목표로 한다.
- **팀 구성**
  | 역할 | 담당 | 주요 작업 |
  |---|---|---|
  | 팀장 / 커널 | 김수아 | xv6 커널, fault injection, 교란 엔진 |
  | CLI | 최우주 | Go CLI, Bubble Tea UI, 로그 파싱, GitHub Actions |
  | 문서/QA/라이선스 | 정수민 | 개발 문서, 진행/중간/최종 보고서, README, 라이선스, QA |

## 2. 진행 현황 요약 (1~3주차)

### 2.1 저장소/협업 체계 구축 (1~2주차)
- Conventional Commits 기반 커밋 컨벤션 확정 (`COMMIT_CONVENTION.md`, `.gitmessage`, `commitlint.config.js`)
- Issue/PR 템플릿 정비 — scope를 `kernel`/`cli`/`docs`/`ci`로 통일, `interface-change` 라벨로 팀원 간 인터페이스(로그 포맷) 변경을 명시적으로 추적하는 체계 도입
- GitHub Actions CI 파이프라인: CLI build & vet, License check (cli 의존성), Kernel build 세 가지 워크플로우 운영 중. License check가 한때 실패했으나 원인은 실제 라이선스 위반이 아니라 go-licenses 툴링 이슈로 확인됨 (섹션 5 참고)

### 2.2 핵심 기술 구현 (3주차)
- **로그 인터페이스 확정**
  - 실패: `[RACEGRADER_FAIL] ASSERT|file:line|SEED|PID|label`
  - 전체 통과: `[RACEGRADER_DONE] SEED|PID`
  - `panic()`(커널 크래시성 실패)과 `cow_test.c`의 `passfail()` 매크로(논리적 오류성 실패) 양쪽 다 반영 완료
- **스케줄링 교란 엔진(chaos engine) 구현**
  - CPU별 독립 xorshift32 PRNG로 락 경계(acquire/release)에 확률적 지연 주입
  - `scheduler()`의 매 라운드 proc 스캔 순서를 Fisher-Yates 셔플
  - 인터럽트 활성 상태에서만 동작하도록 설계해 자체 데드락 위험 없음
  - 실행: `make qemu CPUS=8 SEED=<값> CHAOS=1` (완전 비활성화는 `CHAOS=0`) — 레이스 재현에는 CPUS=8 필요 (CPUS=2로는 경쟁 상황이 거의 안 걸림)
- **오탐률(False Positive Rate) 테스트 설계 및 실측 완료**
  - 정상 동기화 코드가 교란 하에서도 오판정(FAIL)되지 않는지 검증하는 체계 설계
  - baseline(무교란) → 교란 단일 케이스 → 반복 실행 기반 오탐률 측정 3단계로 구성
  - **파라미터 확정**: N=500, SEED=0(시간 기반 자동), CPUS=8, 오탐률 허용 기준 0%
  - baseline(3.1a) 최초 실행 결과는 `main` 오염 상태에서 나온 것이라 무효 처리했으나, 복구 후 재실행 완료 (PASS 1/1, 0%, 커밋 d0d9cb1)
  - 3.2(핵심 오탐 테스트) 실행 완료: 500회 중 FAIL 0건 (0%), 판정 기준 충족
  - `smp_check.c`는 시도했으나 오탐 테스트 대상에서 제외 (성능 비교 방식이라 chaos engine의 지연 주입과 원리적으로 상충) — `cow_test.c`만 채택
- **결함 탐지 실증**
  - `test/kernel-refcount-race` 결함 커널을 500회 반복 실행해 정상 대비 대조 실험 진행
  - 희귀 레이스(500회 중 1회, 0.2%)를 실제로 재현 — 반복 실행 없이는 발견 불가능함을 실증
  - 이 대조 실험이 사용한 "정상(main)" 기준의 재검증 필요 여부는 README 수치 측정 시점 확인 후 확정 예정 (섹션 5 참고)

## 6. 한계점

- **교란 엔진(chaos.c)의 탐지 범위 한계**: chaos.c는 락 경계(acquire/release)에만 훅이 걸려있어, 락을 "잘못 쓰는" 버그(예: refcount-race)는 잘 잡지만, `krefinc()`처럼 락 자체가 "없는" 버그(lock-missing)는 원리적으로 잡지 못한다. 이번 lock-missing 검증(`fork_race.c`)에서는 chaos 엔진이 아니라 CLI TUI 렌더링이 만드는 우연한 스케줄링 지터로 결함이 검출되었으며, `--headless`(CI 환경)에서는 이 지터가 없어 재현율이 낮다는 것도 확인됨. 락 누락 계열 버그에 대한 탐지력 강화는 향후 과제로 남김.
